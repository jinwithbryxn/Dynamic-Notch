# 검증 기록 (notchy-parity)

2026-11-02 통합 빌드에 대해 무엇을 어떻게 확인했고 무엇을 확인하지 못했는지 적는다. 행별 상태는 `FEATURE-MATRIX.md`, 끝까지 되지 않은 행과 이유는 `UNSUPPORTED.md`에 있다.

검증은 세 단계로 나눈다.

1. 빌드: 컴파일과 서명이 되는지.
2. 자체 검사: 앱이 `--module-selftest`로 실제 macOS 호출을 하되 화면·사용자 데이터·시스템 상태를 바꾸지 않고 결과를 확인한다. 화면은 `--render-tab`·`--render-notch`로 앱이 스스로 그린다.
3. 실기: 실제 Mac에서 앱을 띄워 동작을 본다. 검토용 앱(`com.dynamicnotch.app.review`)은 번들 ID가 달라 손쉬운 사용·화면 기록·입력 모니터링·캘린더 등 권한이 하나도 없어, 3절의 검토용 앱 실기에서는 권한이 필요한 경로를 확인하지 못했다. 설치 앱에 권한을 주고 사용자와 함께 확인한 결과는 7절에 있다.

## 4. 실기에서 찾아 고친 문제

### 4.1 종료 요청이 도우미에 먼저 감 (`4672cdb`)

- 증상: 검토용 앱이 종료 요청을 받고도 꺼지지 않아 설치 앱과 함께 떠 있었다.
- 원인: 설정·권한(첫 안내) 창은 같은 실행 파일을 같은 번들 ID의 도우미 프로세스로 띄운다. `tell application id … to quit`이 본 앱이 아니라 도우미에 먼저 가서 도우미만 끝났다. 도우미가 없을 때는 바로 꺼졌다(3회 반복으로 확인). upstream 구조에서 온 동작이며 이번 기능 추가로 생긴 것은 아니다.
- 영향: 설정 창을 연 채로 설치·복원하면 `install-local.sh`가 "did not quit"으로 멈췄을 것이다(교체는 하지 않으므로 안전하지만 설치가 안 됨).
- 수정: `scripts/install-local.sh`와 `scripts/review.sh`가 본 앱과 도우미가 모두 끝날 때까지 2초마다 다시 종료를 요청한다(최대 15초).
- 참고: 검토용 앱과 설치 앱은 명령 채널 이름(`com.dynamicnotch.app.command`)이 같다. 둘을 동시에 띄우면 한쪽에 보낸 명령을 다른 쪽도 받는다. 검토용 앱을 띄울 때는 설치 앱을 끄므로 평소에는 겹치지 않는다.

### 4.2 설정 변경 알림이 끝없이 되풀이됨 (`893e925`)

- 증상: 설치 앱에서 카메라·마이크 표시 기능(`privacy`)을 켜자 CPU를 45% 안팎으로 계속 썼다.
- 원인: 기능이 "설정이 바뀜" 알림을 받으면 `settingsChanged()`에서 같은 값을 다시 저장했고, 저장할 때마다 같은 알림이 다시 나갔다. 자체 검사는 앱을 띄우지 않으므로 이 되풀이를 잡지 못했다.
- 수정: 기능별 설정 저장(`ModuleDefaults.set`)이 값이 그대로면 쓰지도 알리지도 않는다. 한 기능만이 아니라 같은 방식으로 저장하는 모든 기능에 적용된다.
- 확인: 검토용 앱에서 기능 76개를 모두 켜고 하나씩 설정 변경 알림을 보냈을 때 CPU 1–3%. 수정본을 설치한 뒤 1차 시험 기능 5개를 켠 상태에서 CPU 0–2%, 메모리 약 73MB.

### 4.3 시스템 설정에 앱이 두 개로 보임 (`89d9c33`)

- 증상: 사용자가 시스템 설정에서 Dynamic Notch가 두 개 보인다고 알렸다.
- 원인: 검토용 앱도 로그인 항목에 스스로 등록했고, 한국어 표시 이름 파일 때문에 이름이 설치 앱과 같은 "Dynamic Notch"로 보였다. 빌드 폴더에 남은 예전 시험 빌드 10여 개도 LaunchServices에 같은 번들 ID로 등록돼 있었다.
- 수정
  - `scripts/review.sh`: 검토용 앱의 표시 이름을 모든 언어에서 "Dynamic Notch Review"로 바꾸고, 첫 안내(권한 요청) 창을 띄우지 않게 한다.
  - 개발용 실행 인자 `--login-item=off`: 로그인 항목 등록을 지운다. 검토용 앱의 등록을 이것으로 지웠다.
  - `scripts/install-local.sh`: 설치 뒤 빌드 폴더 사본의 LaunchServices 등록을 지운다. 빌드 폴더에는 `.metadata_never_index`를 두어 Spotlight가 사본을 다시 등록하지 않게 했다.
  - 남은 시험 빌드의 등록을 지웠다(파일은 지우지 않음).
- 확인: LaunchServices에 남은 등록은 설치 앱(`/Applications`)과 이름이 다른 검토용 앱 두 개다.
- 같은 날 사용자가 아직 두 개가 보인다고 다시 알렸다. 시스템 설정을 직접 열어 보니 로그인 항목 화면에는 하나뿐이었고, 두 개가 보인 곳은 개인정보 보호의 '손쉬운 사용'과 '화면 및 시스템 오디오 녹음' 목록이었다. 검토용 앱도 이 두 권한을 받아 목록에 따로 올라 있었다. 입력 모니터링·마이크·음성 인식·캘린더·미리 알림·블루투스 목록에는 검토용 앱이 없었다.
- 로그인 항목 DB(`sfltool dumpbtm`)에는 검토용 앱 항목이 꺼진 상태로 남아 있다. 하나만 지우는 도구는 없고 `sfltool resetbtm`은 모든 앱의 항목을 지우므로 쓰지 않았다. 시스템 설정 화면에는 보이지 않는다.
- 검토용 앱 번들은 휴지통으로 옮겼다(`review.sh build`로 다시 만들 수 있다). 권한 목록의 항목은 보안 설정이라 사용자가 각 목록에서 선택한 뒤 "-"로 뺀다.

### 4.4 카메라 장치 감시가 끝없이 되풀이됨 (`55f49bf`)

- 증상: 7.4절 재시험 중 노치 안 '미리 알림 허용' 버튼과 받아쓰기 단축키 ⌃⌥D가 반응하지 않았다. 본 앱이 17:08부터 CPU 96–99%를 쓰고 있었고 메모리는 약 92MB에서 338MB로 늘어 있었다. 명령 채널로 보낸 재시작 명령도 처리되지 않아 `kill -TERM`으로 끝내고 다시 띄웠다(18:02).
- 원인: `privacy`의 카메라·마이크 사용 감시(`CPDeviceUseMonitor`)가 장치 목록 변경 알림 안에서 알림을 모두 떼고 다시 걸었다. 17:08에 iPhone 연속성 카메라 장치(iPhone 카메라, 데스크뷰 카메라)가 나타난 뒤 목록 알림이 이어져 메인 스레드가 이 처리에 묶였다. 멈춘 앱의 `sample`에서 메인 스레드가 장치 속성 알림 처리를 되풀이하고 있었다(기호 없는 빌드라 프레임 구조로 판단). 예전 방식을 따로 재현하니 500번마다 드는 시간이 0.091초에서 0.749초로 늘었다.
- 수정: 목록 알림은 시작할 때 한 번만 건다. 목록이 바뀌면 0.5초 모아 한 번 맞추고, 새로 생긴 장치에만 알림을 걸고 빠진 장치에서만 뗀다. 10초 안에 20번 넘게 맞추면 30초 쉰다.
- 확인: `privacy` 자체 검사에 목록 알림 5000번을 몰아 보내는 항목을 넣었다. 맞추기 2번(시작 + 1), 알림 추가·제거 0번. 수정본을 설치한 뒤 iPhone 카메라 장치가 붙어 있는 상태에서 CPU 0.0–0.3%, 메모리 약 74MB. 10초 20번 제한은 따로 시험하지 않았다.

### 4.5 설정 창이 다른 앱 창 뒤에 열림 (`55f49bf`)

- 증상: 7.4절 재시험 중 설정 창을 열었는데 사용자 화면에 보이지 않았다. CGWindowList로 보니 창은 열려 있었지만 Claude 앱 창 뒤에 있었다. 사용자가 Claude 창을 내리자 보였다.
- 원인(추정): 설정 창은 메뉴 막대 전용 앱의 도우미 프로세스가 띄운다. macOS 14부터의 협조적 활성화에서 앞으로 나오기를 거절당하면 창이 지금 쓰는 앱 창 뒤에 열린다.
- 수정: 도우미가 창을 보일 때 키 창이 아니면 떠 있는 창 높이(floating)로 올리고, 사용자가 창을 눌러 키 창이 되면 보통 높이로 돌린다.
- 확인: 검토용 앱에서 직접 열기, 백그라운드로 열기(`open -g`), Finder가 앞에 있을 때 다시 열기 세 경우 모두 맨 앞에 열렸다. 같은 세 경우를 수정 전 설치 앱으로 해도 맨 앞에 열려, 뒤에 열리는 상황은 다시 만들지 못했다. 수정은 앞으로 나오기를 거절당할 때만 작동하므로 그 경로는 시험하지 못했다.

### 4.6 작업 완료 알림이 두 번, 다른 아이콘으로 뜸 (`55f49bf`, `1326b1b`)

- 증상: 사용자가 Claude 작업 완료 알림의 아이콘이 예전 아이콘으로 돌아갔다고 알렸다.
- 원인: 17:48:18–19에 upstream 완료 훅(`AgentHooks`)이 들어갔다. `~/.claude/settings.json`에 `--agent-done=claude` Stop 훅이 하나 더 생기고, `~/.codex/config.toml`의 notify가 이 앱으로 감싸졌다. 이 훅은 설정 창 'Claude Code · Codex' 페이지의 '연결'로만 들어가므로, 그때 설정 창을 둘러보다 눌린 것으로 본다. 페이지는 기존 알림 스크립트(`~/.local/bin/notch-agent-done`)를 알아보지 못해 '연결 안 됨'으로 보였다. 이 훅은 SF 기호("sparkle") 카드를 띄우고 백그라운드 작업·하위 에이전트 거르기가 없어, 실제 앱 아이콘을 쓰는 기존 스크립트 알림과 함께 두 번 뜬다. 또 settings.json을 `JSONSerialization`으로 다시 써서 파일 전체의 키 순서와 띄어쓰기가 바뀌었다.
- 되돌림: 두 파일을 `*.bak-20261102-dupehook`으로 남겼다. settings.json은 내용이 같은 2026-10-27 사본(`settings.json.dynamicnotch.bak`)으로 글자까지 되돌렸고, config.toml은 notify 줄만 17:48 전 줄로 되돌렸다(`config.toml.dynamicnotch.bak`과 같음).
- 수정
  - 설정 페이지가 notch-agent-done이 이미 연결돼 있으면 '연결됨 (알림 스크립트)'로 보이고 연결 버튼을 숨긴다. `AgentHooks.install`도 이때 건너뛴다.
  - settings.json을 `OrderedJSON`으로 읽고 써서 연결·해제 때 키 순서와 모양을 지킨다.
  - Claude Code·Codex는 세션을 시작할 때 훅 설정을 읽어 두므로, 훅을 뺀 뒤에도 그 사이에 시작한 세션(17:51에 시작한 Claude Code 세션 하나)이 옛 훅을 계속 부른다. 훅 프로세스는 설정 파일에 그 훅이 아직 있을 때만 알린다. Codex의 원래 notify 명령은 그대로 실행한다.
- 확인: 자체 검사(사본)에서 스크립트 인식, 연결 뒤 해제 시 1257바이트 그대로. 설치 앱 실행 파일로 옛 Claude 훅을 불렀을 때 알림이 나가지 않음(알림 수신기로 확인했고, 수신기가 받는지는 시험 알림으로 먼저 확인). Codex 감싸기 경로로 부르면 원래 명령은 실행되고 알림은 나가지 않음. 이후 사용자가 다음 Claude 완료 알림이 실제 Claude 아이콘으로 한 번 뜬 것을 확인했다(2026-11-03). 같은 시각 `~/Library/Logs/notch-agent-done.log`에 스크립트 경로의 `posted` 기록이 있고, `~/.claude/settings.json`에는 `--agent-done=claude` 훅이 없다.
